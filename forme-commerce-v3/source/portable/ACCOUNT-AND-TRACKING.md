# FORME v3 — launch and operations guide

This guide covers the two separately deployed sites in this package. The customer website, admin studio, database, payment server, authentication provider, and mail sender are distinct services. A prebuilt UI alone cannot activate Google sign-in, send emails, or process a charge. Complete the settings below with your own accounts.

## What customers and admins can do

- Customers can create an email/password account or continue with Google, edit saved name/phone/address, request an email change or password reset, see account orders, and follow a merchant-updated shipment timeline. Supabase Auth stores the Google identity and login; order rows reference the same Auth user ID. Guest checkouts keep their private receipt link.
- The customer storefront has eight interface languages: English, Mongolian, Traditional Chinese, Simplified Chinese, Japanese, Korean, Russian, and Spanish. The language choice stays on the device. Checkout and account controls use the selected language. Product names/descriptions and policies are merchant content and stay as entered. Admins can write translated campaign copy for every offered language in Studio → Store settings. Blank translations fall back to the main copy.
- Admins edit products, images, stock by option, price, store identity, home campaign, story, policies, language copy, shipping fees, payment mode, and order tracking. Saves are written to the shared database and appear on the customer website without rebuilding. Admin pages are English.
- Shipping stages are **Preparing → Shipped → Out for delivery → Delivered**. An admin enters the real carrier, number, and HTTPS tracking URL. This does not poll a carrier or independently prove delivery. Payment verification remains separate from shipping status.

## A. Database and identity

1. Create one Supabase project. For a brand-new project, run `database/schema.sql` in SQL Editor. For an existing FORME v2 project, back up the database, then run `database/upgrade-v3.sql` once. For a legacy v1 project, run `database/commerce.sql` and then `database/upgrade-v3.sql` in that order. Never run the fresh schema against an existing project.
2. In Authentication → Providers, enable **Google**. In [Google Cloud Console](https://console.cloud.google.com/apis/credentials), configure the OAuth consent screen and create a **Web application OAuth client**. Google's redirect URI must be the callback URL displayed in Supabase's Google provider settings, normally `https://PROJECT_REF.supabase.co/auth/v1/callback`. Paste the Google client ID and secret into the Supabase provider settings, never into `config.js`. Read [Supabase's Google setup](https://supabase.com/docs/guides/auth/social-login/auth-google).
3. Set Supabase Auth Site URL to the final customer HTTPS origin. Add the exact customer return URL used by this app, `https://YOUR-SHOP.netlify.app/?account=1`, to Auth → URL Configuration → Redirect URLs. If using a custom domain, add that exact domain too. Read [Supabase redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls). Test a Google sign-in from a private browser window and confirm the new identity in Authentication → Users.
4. Enable email/password if desired. Leave email confirmation and **Secure email change** enabled. Configure production SMTP and the confirmation/recovery templates in Supabase; the default hosted mail rate limits are for evaluation, not a production mailing system. Verify signup, reset, and the two confirmation links for changing email. Password changes can require a reauthentication nonce depending on your Supabase security setting; if the provider rejects a change, use the recovery flow. Never bypass that policy in the client. See [Supabase update user](https://supabase.com/docs/reference/javascript/auth-updateuser) and [email templates](https://supabase.com/docs/guides/auth/auth-email-templates).
5. Create a separate admin Auth user and run `database/create-admin.sql` with that user's actual email. Only that row grants Studio access. A Google customer account never becomes an administrator merely by signing in. Confirm the role in a second, private browser session.

## B. Deploy the customer and management sites

1. Deploy `customer-site/` as one Netlify Git project. Its `netlify.toml` publishes the prebuilt `web/` and bundles `functions/`. Deploy `management-site/` as a second Netlify Git project. For each new version of this kit, replace the matching files and redeploy both.
2. In **both** `web/config.js` files, enter the same Supabase URL and publishable key and the real customer and management HTTPS origins. The Studio `apiBase` must point to the customer deployment's `/.netlify/functions`. A publishable key is public; a service-role key must never be here.
3. Set customer Netlify Functions environment variables from `customer-site/checkout.env.example`: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `STORE_ORIGIN`, `MANAGEMENT_ORIGIN`. Put these only in server environment settings and redeploy after changing them. Use HTTPS, exact origins, no trailing slash. Admin data is guarded by Supabase RLS and the server-side admin function check.
4. Configure one merchant provider following `START-HERE.md` and test a complete payment and webhook. Google registration is not a payment integration. Do not accept real orders until your own catalog, policies, merchant account, and delivery process are ready.
5. Confirm the admin's saved brand edits appear on the storefront, then test size stock, a guest checkout, a signed-in checkout, an order in the account, and a shipment update with the real carrier URL. A signed-in order is attached to the Auth user at checkout; older guest orders are not silently claimed by matching email.

## C. Account and shipment email alerts

1. Verify a sending domain with [Resend](https://resend.com/domains) and add its DNS records. Set `RESEND_API_KEY` and `MAIL_FROM` (for example `FORME <orders@your-domain.com>`) in the **customer Netlify server environment**. Redeploy Functions. Never put these values in the web config or Git repository.
2. Profile, password, and email-change requests are authenticated against the current Supabase user. The server updates the account and sends a plain-text alert to the **previously verified account email**, not an email supplied in the request. Changing email also uses Supabase's confirmation workflow. Tracking updates are authorized by the database's admin-only RPC and alert the order's saved email.
3. When a mail provider is unavailable, a saved change is explicitly reported as saved **without** an email notification. Check customer Functions logs and your provider dashboard, then fix the sender/domain. Delivery acceptance by a mail API is not proof of inbox arrival. Resend's [send API](https://resend.com/docs/api-reference/emails/send-email) documents the sender requirements and response.
4. Restrict who holds the admin account, monitor mail and order logs, and rotate exposed server keys. The browser never receives the service-role key or mail API key.

## D. Hosted Sites preview

The ChatGPT Site at `/manage` continues to use Sites' built-in ChatGPT identity and Cloudflare D1/R2. It is owner-private and remains private in this release. The hosted customer profile stores name, phone, and address in D1; orders and admin-entered tracking appear in its account view. Its email and password belong to the platform identity, so password/email edits and Google OAuth are **not** provided there. The Google flow above is for your separately deployed public customer website. Set `RESEND_API_KEY` and `MAIL_FROM` as Sites runtime secrets if you want hosted profile/tracking alerts; without them, the UI reports that the email was not sent. A public customer deployment requires your own configured Supabase project and two-site setup above.

## E. Visual identity and content

FORME's editorial design, copy, layout, logo treatment, and admin studio are original to this project. Replace every sample product/photo with your own licensed product assets and describe items accurately. In Studio → Store settings, adjust the campaign label/headline, two hero images, collection heading, story heading/image, announcement, language variants, contact details, policies, and checkout settings. In Products, edit category, size/color variants, image gallery, and inventory. This is a maintainable store system, not a copy of another retailer's branding.
